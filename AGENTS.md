# AGENTS.md

Guide for coding agents working on bee-factory. Read it before changing anything.

## Project

bee-factory (`@ethersphere/bee-factory`) is a CLI that starts a local Swarm development stack in Docker: one Anvil chain and five Bee full nodes (a queen and four workers) with Swarm's contracts deployed, wallets funded, and a SWAP cheque and reserve sample ready. bee-js, swarm-cli and other projects run their integration tests against it.

`SPEC.md` is the source of truth for behaviour: CLI, ports, keys, contracts and the startup sequence. Read it first, and update it when behaviour changes. `README.md` is the user-facing summary, and `docs/troubleshooting.md` covers common failures.

## Structure

| Path | Contents |
| --- | --- |
| `bin/bee-factory.js` | Executable entry, loads `dist/cli.js` |
| `src/cli.ts` | yargs commands and options (`start`, `stop`) |
| `src/commands/start.ts`, `stop.ts` | Command orchestration: the startup sequence from `SPEC.md` |
| `src/config.ts` | Fixed constants: ports, container names, images, test keys, funding amounts |
| `src/docker/manager.ts` | All dockerode work: images, network, containers, readiness waits, peer mesh, prebuilt Docker Hub images |
| `src/blockchain/` | Contract deployment, wallet funding, Anvil snapshot save and restore |
| `src/keystore/` | V3 keystore generation for the node keys |
| `src/services/traffic_generator.ts` | Uploads that make worker 1 issue a cheque to worker 2 |
| `contracts/` | Solidity sources, compiled with hardhat |
| `src/contracts/artifacts/` | ABI and bytecode bundled in the npm package (generated by `npm run compile-contracts`) |
| `scripts/test-smoke.sh` | Smoke test against a running stack |
| `.github/workflows/` | Release, npm publish, Docker image publish, smoke test and PR pipeline checks |

Prebuilt images: `publish-images.yaml` runs `start --fresh` on pushes to `master`, commits the six stateful containers as `ethersphere/...` images and pushes them to Docker Hub. `start` pulls them when available (`tryPullPrebuiltImages`) and falls back to building Bee from source.

## Commands

```sh
npm install
npm run prepare                      # compile contracts, copy artifacts, tsc
npm run dev -- start                 # run the CLI from source
./bin/bee-factory.js start --fresh   # run the built CLI, redeploying contracts
./bin/bee-factory.js stop
./scripts/test-smoke.sh              # needs a running stack, swarm-cli and jq
```

Docker is required. A fresh start builds Bee from source, which takes several minutes.

## Constraints

- Keep the fixed values fixed: node keys, password, ports, chain ID, the whitelisted withdrawal address and the funding amounts. Downstream test suites hardcode them. Changing one is a breaking change and must update `SPEC.md` and `README.md`.
- The keys in `src/config.ts` are public Foundry test keys and must stay that way. Never add real secrets.
- `start` must always begin from a clean slate (remove existing containers and the network), and `stop` must remove everything it created.
- Every wait for a container or API needs a timeout and a clear error message.
- Support new Bee versions without breaking older ones. When Bee changes flags, detect the version and keep backward compatibility.
- Recompile and commit `src/contracts/artifacts/` whenever `contracts/` changes.

## Coding style

- TypeScript (strict), CommonJS output, Node.js 18+.
- Semicolons, single quotes, 2-space indent, trailing commas in multi-line literals. Match the surrounding code, since there's no formatter config.
- Named constants in `src/config.ts` instead of magic numbers or strings in the logic.
- Small, well-named functions. `src/docker/manager.ts` and `src/commands/start.ts` are large, so put new logic into focused helpers or modules rather than growing them.
- `async`/`await` throughout. Use `ora` spinners for progress and `chalk` for status output, as the existing commands do.

## Comments: strict rule

Write code that is easy to read, so it doesn't need comments. Comments must not explain unclear code; rewrite the code instead.

- Default to no comments.
- Before adding one, try better names, a well-named helper function or a named constant.
- If a comment is still needed, for a non-obvious "why" such as a Bee or Docker quirk, keep it to one short line.
- No multi-line block comments, no comments that restate the next line, and no commented-out code.
- When you edit code that has verbose comments, shorten or remove them.

## Git and releases

- Conventional Commits (`feat:`, `fix:`, `chore:` ...).
- `master` is the trunk. release-please opens release PRs from it, a GitHub release publishes the npm package, and every push to `master` republishes the prebuilt Docker images.
